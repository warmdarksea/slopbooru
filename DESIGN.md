# imgrec: the recognition pipeline as a service

Replaces `src/py-pipeline` (classify/infer/cache/store) with one Go
program, `imgrec`. Python stays only inside the model runtimes.

## Two kinds of process

**Runners** hold a model in VRAM. Loading takes 1-2 minutes, so they are
long-lived: started once, used for many images, stopped to free the card.

- `vllm serve <weights>`: one per chat model, OpenAI HTTP on 127.0.0.1.
- the pixai worker (`runners/pixai_worker.py`): loads torch and the
  model once, then reads image paths from stdin and writes one JSON line
  per image to stdout, batching whatever is waiting. Not faster per image
  on a big batch (the forward pass owns the GPU either way), but a
  single image no longer pays ~10-20 s of python, torch, CUDA and model
  load before it is tagged.

**imgrec** is the service. It never imports torch or CUDA. It owns:
starting and stopping runners (that *is* model loading; the scheduler
decides which are up), each model's spec, the cache, the store, the
queue, and the HTTP API with clients and tokens.

There is one adapter per *kind* of model (fields, caption, ocr, guard,
tagger): how to build its request and read its reply. Models themselves
are data.

## Specs: every parameter, in one place

A spec is everything that determines a model's answer, generated by the
flake from `fleetSpec` (as `models.json` is today) so it's pinned with
the weights:

- `name`, `kind`, `weights` (store path), `closure`
- `runner`: the output-affecting server settings (`max_model_len`,
  image `max_pixels`, `--generation-config vllm` so *nothing* is
  inherited from the weights' generation_config.json), plus the
  non-affecting ones (gpu fraction, max_num_seqs) kept separately
- `request`: the full request minus the image -- prompt, system prompt,
  response schema, temperature, top_p, top_k, max_tokens, logprobs,
  chat_template_kwargs
- `output`: the fields it produces (JSON schema)
- `needs`: models whose answers it reads (llamaguard: the describer)

**Seed**: per request, derived from the input's sha256, so a re-run
reproduces the cached answer instead of drawing a new sample.

## The cache rule

    key = sha256(canonical(question spec) || input sha256 [|| context])

where the question spec is `weights`, the output-affecting `runner`
settings and `request`. Hit: use it. Miss: run it and write it. The key
is also the provenance identity and the resume check -- one identity
instead of today's three.

Deliberately *not* in the key, but recorded with every answer: the
engine (vllm version, launcher), so an upgrade doesn't re-run everything.
`--no-cache` for runs that compare engines.

The input is the bytes the model is shown: the original, or the
downscaled stand-in for an oversized image.

## Records are the output; the db is derived

A **record** is one answer: `{key, model, spec_hash, image_sha,
input_sha, raw reply (verbatim), elapsed, engine, at}`. Raw, so a parser
fix re-reads answers already paid for.

Two record backends, same interface (`get(key)`, `put(record)`, `scan`):

- **sqlite**: a table in `results.db` (today's `cache_*`, reshaped)
- **jsonl**: one append-only file per machine; merging machines is
  concatenating files and importing, and keys never conflict

The **store** (images, provenances, annotations: today's schema, which
the booru reads) is built from records by parsing them. Import is
idempotent, so rebuilding is always safe.

## Three abstractions

- **Runner**: `Start(ctx)`, `Ready()`, `Stop()` (SIGTERM, wait, SIGKILL),
  `Kill()`. Implementations: vllm (subprocess + `/health`), stdio (the
  pixai worker). Stop kills the whole process group (vllm's workers hold
  the VRAM) and returns only once the VRAM is actually free.
- **Model**: spec + adapter. `Key(input)`, `Request(input)`,
  `Parse(raw)`, output schema, which runner. Input = image (original or
  stand-in) bytes + sha, and for the guard its context text.
- **Job**: one image on one model. Intake:
  1. compute the key; record in the cache -> done (200 + result)
  2. else ensure a `jobs` row (image sha, model, client) -> queued (202)
  3. a model that `needs` another (llamaguard reads the describer's
     answer) first runs intake for that dependency; the job waits until
     the dependency's record exists

  When a runner finishes a job, its record goes in the cache and the job
  row is deleted -- running intake again is a cache hit. `jobs` only
  ever holds outstanding work; a crash loses nothing (rows stay, the
  answer just isn't there yet).

- `jobs(model, image_sha, client, created, attempts, last_error)`,
  unique on (model, image_sha, client)
- images live content-addressed on disk (`images/ab/abcdef...`, plus
  stand-ins), so `jobs` refers to them by sha only

## The scheduler

The constraint is VRAM, not job count, and loading costs 1-2 minutes.

- dispatch from runners already up first (switching costs minutes; a
  trickle of small jobs must not keep evicting a big model mid-batch);
- when those have nothing to do, start the **smallest** waiting model
  that fits (gpu fractions), so quick answers come out first;
- start runners one at a time (vllm sizes its KV cache from memory
  measured at startup; a neighbour starting concurrently makes it lie);
- feed each at its concurrency, **round-robin between clients** for
  jobs on the same model;
- stop an idle runner when another model is waiting for room;
- **rotate**: a runner that has been up longer than the rotation period
  (default 2 h) gives way when another model has jobs waiting and can't
  fit beside it, even if its own queue is still being refilled -- so a
  steady stream for the big model can't starve everything else. It
  finishes the requests in flight, stops, and its leftover jobs wait
  their turn like any others.

That's today's fixed `PHASES`, made dynamic.

## HTTP API

All calls carry `Authorization: Bearer <token>`. Every call is
idempotent: asking twice is asking once.

- `GET /v1/models` -- name, kind, output schema, spec hash
- `PUT /v1/images/{sha256}` -- the bytes (hash verified): 201 stored,
  200 already had it
- `POST /v1/jobs {image, model}` -- 200 + result (cache hit), or 202 +
  `Location: /v1/jobs/{model}/{sha}` (queued or already queued)
- `GET /v1/jobs/{model}/{sha}?wait=N` -- 200 + result, 202 still pending
  (after holding up to N s), or the failure
- `DELETE /v1/jobs/{model}/{sha}` -- cancel, if it hasn't run

**The client needs no queue**: its pending set is its own input list.
`GET /v1/models`, upload each image, POST each (image, model), then GET
the 202s with `?wait=60` until they are 200. A crashed client is re-run
with the same inputs: what finished comes back 200 at once, nothing is
queued twice.

## Clients (tenancy) and auth

- `clients(id, name, token_hash, admin, created)`; `imgrec client add
  NAME [--admin]` prints a token once; the db keeps only its hash
- a client sees the images it submitted; an image two clients submitted
  is visible to both and still runs once (results are keyed by content)
- admin sees everything and manages clients
- the queue takes turns between clients

## Several machines

Each machine runs `imgrec` with the jsonl backend over a disjoint share
of the work (image sha mod N); results merge by import. Leases only if
duplicated work ever matters -- it is wasteful, never wrong.

## No cache migration

The python pipeline's caches are not imported: imgrec starts with an
empty cache (the user's call). `imgrec import-py-cache` exists only as
the parity test's tool.

## Testing

- **replay parity**: parse every record in an existing `results.db` with
  the Go adapters and import into a fresh db; the rows must equal what
  the python store holds
- stub runners, as today: a fake `vllm` serving canned replies and a fake
  pixai worker, so scheduling, dependencies, failures, the API and auth
  test without a GPU
